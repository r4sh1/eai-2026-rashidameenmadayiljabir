# ADR-005 — Checkout as an orchestrated saga behind a contract written first

**Status:** accepted
**Date:** 2026-10-21

## Context

I wrote `openapi.yaml` before any orchestrator code. Spectral made me decide things I would have left open.

The `no-unbounded-arrays` rule failed on `items` in the bad example. So I had to pick a bound for the order. I chose 20.
The same rule hit the trace. I counted the worst case: four forward calls plus two compensations. That gave `maxItems: 6`.
The `error-responses-have-schema` rule forced me to name every error shape. That is why `500` and `internal_error` are in the contract.

The canonical schema does not bound `items`. The given validation would accept 21. My contract says 20, so I had to enforce it.

Shipping and notification have no compensating endpoint. When notification fails, I release inventory and refund payment. The shipment stays created.

A timeout needed its own rule. With shipping delayed by 6000 ms, my call gave up after 2510 ms. The request took 2.61 s. That is a 504, not a 422.

Test 9 sends a second request with the same key while the first waits on shipping. It reads an `in_progress` record. It needs its own answer: `409` with `idempotency_conflict`.

My baseline run left `not_implemented` results in `orchestrator/data/`. They survived the rebuild. A stored result replays forever under its key.

## Decision

`validateCheckoutPayload` checks the canonical schema, then `MAX_ITEMS = 20` and a minimum of 1. A failure is `400` with `validation_error`.

`computeAmount` sums `unitPrice × quantity` in whole cents with BigInt. It formats the string once. `3 × 0.10 + 0.20` gave `"0.50"`.

`callDownstream` makes one call and records one trace entry. It never throws.
Its own timer fires after `REQUEST_TIMEOUT_MS`. That, or an axios `ECONNABORTED` or `ETIMEDOUT`, is a timeout.
Any answer outside 2xx is a failure, with the code from the body. A refused connection is `downstream_unavailable`.

`runSaga` runs the four steps one after another. It keeps an undo list of the steps that succeeded. On a failure it runs that list newest first: `inventory_release`, then `payment_refund`.
If an undo fails, it still tries the rest. Then it answers `422`, `status: "failed"`, `code: "compensation_failed"`. I saw this with inventory and refunds both set to fail.
Otherwise a timeout is `504` and a business failure is `422`. Status is `compensated` if something was undone, `failed` if payment itself failed.

A replay returns the stored status and body unchanged. Payment is not called again. A different body under the same key is `409` with `idempotency_payload_mismatch`.

The handler writes the `in_progress` record before its first `await`. Read and write happen in one synchronous block, so two requests cannot claim one key.

`persistResult` re-reads both stores right before writing, because another request may have written them during the awaits.
`releaseKey` deletes the claim after an unexpected error. The client gets `500` and can retry.

## Alternatives considered

**Choreography, as in PA5.** Each service reacts to an event. I rejected it. The caller needs one synchronous answer with a status code and a trace. Nobody would own the step order or the rollback.
With orchestration I lose independence. One process now knows every service and is a single point of failure.

**Compensating endpoints for shipping and notification.** Rejected. The mock services are not mine, and they are replaced at grading. A sent notification cannot be unsent.
The cost is real. A failure after shipping leaves a shipment nobody cancels.

**Parallel calls.** Rejected. Payment must succeed before stock is reserved.

## Consequences

A fifth step is one more entry in the `steps` list in `runSaga`. But the trace bound of 6 then lies. I must raise it in the contract.

Two requests with different keys and the same `orderId` are not detected. Both would charge payment. The second saga record overwrites the first. This breaks first.

If the orchestrator is killed mid-saga, the `in_progress` record stays. Every later request with that key gets `idempotency_conflict`, forever. Payment may be authorized and never refunded.
I accepted this cost. A claim timeout would fix it, and I did not build one.

Both stores are whole JSON files, rewritten on every request. They are simple and survive a restart. They will not scale.
