# ADR-000 — Legacy Fixed-Width and Dual-Encoding File Ingestion

**Status:** Accepted

**Date:** 2026-09-10

## Context

The integration system processes legacy order exports (`data/orders-20260901.txt`) together with customer master records (`data/customers.csv`) provided by an upstream department system. The input files introduce several integration challenges that can result in silent data corruption or data loss.

1. **Different Character Encodings**

   The customer CSV file is encoded in UTF-8, while the order file uses Windows CP1257 (`windows-1257`). Reading the order file as UTF-8 can corrupt Latvian characters such as `Jānis Bērziņš` and `Šmite`, potentially producing values such as `J?nis B?rzi??` and `?mite` without generating a runtime error. This makes the problem difficult to detect because the resulting data may still appear valid.

2. **Fixed-Width Records and Whitespace**

   Order records use fixed character positions, with fields left-aligned and padded with spaces. Standard whitespace-based parsing, such as `line.split(/\s+/)`, cannot reliably process these records because customer names and other fields may contain internal spaces.

3. **Malformed Records**

   Line 6 of the order export contains only 26 characters instead of the required 77 characters. Stopping the entire process when this occurs would prevent valid orders from being processed. However, silently ignoring the record would result in data loss without an audit trail.

4. **Date and Monetary Value Representation**

   Order dates use the `DD.MM.YYYY` format rather than the standard ISO format. Converting these values directly with JavaScript's `Date` object can introduce parsing and timezone-related issues.

   Monetary values use commas as decimal separators, for example `1234,56` and `-250,00`. Converting these values with `parseFloat` can remove trailing zeros, such as converting `"45.20"` to `45.2` or `"7800.00"` to `7800`. This is undesirable when exact monetary representation must be preserved.

## Decision

A robust ingestion handler was implemented in `starter/src/ingest.ts` through the `ingest()` function. The implementation uses the following design decisions:

1. **Native Character Decoding**

   The order file is decoded using Node.js's built-in `TextDecoder("windows-1257")` through `decodeOrderFile()`. This correctly preserves CP1257 characters without requiring an external package such as `iconv-lite`.

2. **Positional Column Slicing**

   The fixed-width structure is defined using the `ORDER_LAYOUT` column boundaries. Each field is extracted using its exact character positions with `line.slice(start, end).trim()`.

   This approach ensures that internal spaces within values, such as customer names, do not affect field boundaries.

3. **Non-Blocking Error Handling**

   Each order line is validated against `ORDER_LINE_LENGTH = 77`. Invalid or truncated records are added to a dedicated `rejected` collection containing the 1-based line number, raw content, and reason for rejection.

   This allows valid records to continue processing while still providing an audit trail for invalid data.

4. **String-Based Data Conversion**

   * **Dates:** `DD.MM.YYYY` values are converted to ISO `YYYY-MM-DD` strings using `toIsoDate()`. This avoids relying on JavaScript `Date` parsing and prevents timezone-related issues.

   * **Amounts:** Commas are replaced with decimal points using `toDecimalString()`. Monetary values remain strings rather than being converted to floating-point numbers, preserving trailing zeros, precision, and negative values.

5. **Set-Based Customer Matching**

   Customer IDs are extracted from `customers.csv`, excluding the CSV header. The accepted order customer IDs are then compared against these IDs using a JavaScript `Set`.

   This provides an efficient way to identify customer records referenced by the orders but missing from the customer master data.

## Alternatives considered

1. **Using Third-Party Dependencies such as `iconv-lite` or `csv-parser`**

   **Rejected.** Node.js provides native support for `windows-1257` through `TextDecoder`, and the customer CSV has a simple, non-quoted semicolon-separated structure. Avoiding unnecessary dependencies keeps the implementation lightweight and satisfies the project constraints.

2. **Regular Expression Parsing Instead of Positional Slicing**

   **Rejected.** Regular-expression or whitespace-based parsing can incorrectly interpret padded fields and values containing internal spaces. Positional slicing is deterministic and better suited to fixed-width legacy records.

3. **Using `parseFloat` for Monetary Values**

   **Rejected.** `parseFloat("45.20")` produces `45.2`, removing the trailing zero. Keeping monetary values as decimal strings preserves their original precision and representation.

4. **Throwing an Exception for Malformed Records**

   **Rejected.** Throwing an exception for the malformed sixth line would terminate the entire ingestion process. A structured `rejected` collection provides visibility into invalid records while allowing valid orders to continue processing.

5. **Replacing the File-Based Integration with a Modern JSON/REST API**

   **Considered.** A REST API using UTF-8 JSON and an OpenAPI-defined schema would be preferable as a long-term solution. However, the current integration must support the existing legacy file-based system, so this was not selected for the current implementation.

## Consequences

### Benefits

* No external runtime dependencies are required.
* Latvian CP1257 characters are decoded correctly.
* Malformed records do not stop the entire ingestion process.
* Invalid records are retained in `rejected[]` for auditing and troubleshooting.
* Fixed-width records are parsed deterministically.
* Monetary values retain their exact decimal representation.
* Date conversion avoids JavaScript timezone and parsing issues.

### Risks and Limitations

* The fixed-width layout is dependent on the `ORDER_LAYOUT` specification. If the upstream system changes column positions or adds fields, the offsets must be updated manually.
* The ingestion logic assumes that the order file continues to use Windows CP1257. If the upstream system saves the file as UTF-8 instead, decoding it as CP1257 may produce incorrect characters.
* The current implementation is designed around the known structure of the legacy files and would require changes if the upstream format evolves.
