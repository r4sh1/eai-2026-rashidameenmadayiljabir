# ADR-004 — Correlation id in a header, deduplication in a file

**Status:** accepted
**Date:** 2026-10-10

## Context

The order has to reach payment, inventory and notification. The canonical order schema forbids extra fields, so the correlation id cannot go in the body. It has to travel on the message itself. AMQP has two places for it: the native `properties.correlationId` and a key inside `properties.headers`. They look alike and are different fields.

In my run I forced `PAYMENT_FAIL_RATE=100` and posted an order. The payment log for `c0ac780c-8718-4d4e-8b81-3efa9b24c9e8` showed attempt 1, Retry, attempt 2, Retry, attempt 3, then "DLQ after 3 attempts". The retry count needs care. One retry cycle dead-letters a message twice, once as `rejected` and once as `expired`, so `x-death` gets two entries per failure. On the third attempt `getRetryCount` returns 2, which is why the check is `retryCount >= MAX_RETRIES - 1` and not `>= MAX_RETRIES`.

Notification-service also received an order it had already logged. The log showed `duplicate skipped: 4fe6ff52-d16c-4929-95b4-a3eca1f87816`. RabbitMQ delivers at least once, so the receiver has to cope with repeats.

## Decision

**Correlation id.** `order-service` generates a UUID and publishes the order body unchanged with `headers: { correlationId }` and `persistent: true`. I did not use `properties.correlationId`. Every consumer reads `msg.properties.headers["correlationId"]` and copies it onto its result message.

**Processed.** In notification-service, "processed" means the correlation id is in the array stored at `/data/processed-ids.json`. `loadProcessedIds` reads the file on every message and `saveProcessedIds` writes it back. The duplicate check runs first. The handler then appends the log line, saves the id, publishes the result and acks, in that order.

**Permanent.** Each consumer has a `PermanentError` class. Two cases throw it: a missing `correlationId` header, and a body that is not valid JSON. `JSON.parse` is inside the `try` so a bad body is classified and does not crash the consumer. A permanent failure is published to `orders.invalid.exchange` with the original bytes and headers, then acked. I tested this with the body `{ not json` and the header `correlationId: test1`. `orders.invalid` received 3 messages, one per consumer, each 10 bytes, with no `x-death` header.

**Replay.** The handler for `POST /dlq/replay` in order-service takes messages from `orders.dlq` one at a time. It republishes the original bytes to `orders.return.exchange` with the `originQueue` header as the routing key, so only the consumer that failed gets the message. `withoutRetryHistory` removes the `x-death` history, so the message starts with a fresh retry count. After replay the payment log showed attempt 1 and then OK for the same id, and the response was `{"replayed":1}`.

## Alternatives considered

**An in-memory `Set` for processed ids.** I rejected it because the state is lost when the container restarts. After `docker compose restart notification-service`, a redelivered order would be logged a second time, which is the failure the idempotent receiver exists to prevent. The file costs more per message, because the whole array is read and rewritten each time. I accepted that for this volume.

**Replaying through `orders.exchange`.** That exchange is a fanout, so a replayed payment failure would also reach inventory and notification. Inventory has no dedup check and would reserve stock a second time. Routing through the direct `orders.return.exchange` with `originQueue` as the key limits the replay to one queue.

## Consequences

**What is easier.** A malformed message shows up in `orders.invalid` at once, not after three retries and a trip through the DLQ.

**What breaks first.** A future consumer that forwards a message without copying the header would lose the correlation id, and nothing would report it. Two notification replicas sharing one `processed-ids.json` could both read before either writes, and log the same order twice.

**Costs I accepted.**
- If the process dies after the log line and before `saveProcessedIds`, the order is logged again after a restart.
- Only the two cases above are permanent. A body that is valid JSON but not an order, such as `{}`, passes the JSON check, throws a `TypeError` on `order.customer.email` in notification-service, counts as temporary and ends up in the DLQ after three attempts.
- Replay does not check whether the cause of the failure is fixed. If it is not, the message gets a fresh set of three attempts and returns to the DLQ.
