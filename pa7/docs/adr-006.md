# ADR-006 — Using Temporal for the Checkout Saga

**Status:** accepted
**Date:** 2026-10-22

## Context

In PA6, the orchestrator lost track of a checkout when it crashed during shipping. I set the shipping delay to 2000 ms, started a checkout with the key `crash-6`, and killed the `pa6-orchestrator` container during the shipping call.

After the crash, payment had been called once for `63.90`, and shipping had been called once. `saga-store.json` was empty, because `persistResult` only saved the result after the entire saga finished.

`idempotency-store.json` still held `crash-6` in state `in_progress`. Sending the same request again returned `409 idempotency_conflict`. Nothing was running, and the record would never be cleared. The customer had been charged, but the order was unfinished.

Two more problems came up. Declined payments should not be retried, while silent services should be. And shipping ran twice during the PA7 crash test.

## Decision

The workflow is in `worker/src/workflows/checkout.ts`. It calls six activities from `worker/src/activities/index.ts`: `authorizePayment`, `reserveInventory`, `createShipment`, `sendNotification`, `refundPayment` and `releaseInventory`. The workflow does no I/O.

Each activity has a `startToCloseTimeout` of 2500 ms, matching PA6's `REQUEST_TIMEOUT_MS`. Each has three attempts, starting at 200 ms and doubling.

The `post` helper decides which errors can be retried. A `4xx` is non-retryable, because the request will fail again. A `5xx` or a missing response can be retried. If the mock gives no error code, the helper uses `<step>_failed`, as in PA6. I set no Axios timeout, so a slow call reaches the workflow as a `TimeoutFailure`.

`runStep` executes an activity and records a trace entry. `codeOf` turns a failure into an error code or `timeout`.

If a step fails, `compensate` releases inventory first and then refunds the payment. It tries every compensation even if one fails. If any fails, the result is `failed` with `compensation_failed`. The workflow returns a `CheckoutResult` and never throws. A replay with the same key returns the stored result, because the api uses the key as the `workflowId`.

## Alternatives considered

I considered keeping the PA6 orchestrator and adding a recovery job that scans `idempotency-store.json` for `in_progress` records.

PA6 kept completed steps in the in-memory `undos` array. I would need to save progress after every step. Even then, I could not know whether a call had succeeded before a crash. My test showed that shipping had already reached the mock. I would also need a lock, so two orchestrators do not recover the same saga.

I rejected it because I would be building my own workflow engine.

## Consequences

Easier: a worker crash no longer loses the saga. In the PA7 crash test (`crash-2`), payment was called once, shipping twice, and the saga completed.

Shipping ran twice because the first request reached the mock before the worker died. Temporal cannot know whether it succeeded without the response. If payment ran twice, the customer could be charged twice. My activities send only `orderId` and `amount`, so the payment service should use `orderId` to prevent duplicate charges.

Slower: the crash test took about 20 seconds, including a workflow task waiting about 10 seconds for the dead worker.

Harder: changing the order of steps can break replay of running workflows, so I would need workflow versioning.

I now run and monitor both Temporal and the worker. If the worker is down, checkouts wait until the API gives up. I accepted these costs for recovery and automatic retries.

## What the engine took over

- Timeouts: PA6's `callDownstream` used an `AbortController` and an Axios timeout. In PA7, `startToCloseTimeout` does it, and `codeOf` reads a `TimeoutFailure`.
- Progress tracking: PA6 kept the in-memory `undos` array in `runSaga`. In PA7, the workflow history records every step result.
- Idempotency: PA6 wrote `in_progress` in `POST /checkout`, and `persistResult` or `releaseKey` cleared it. In PA7, the workflow ID is the request key, and `REJECT_DUPLICATE` blocks duplicate starts.
- Recovery: PA6 used `readJsonFile` and `writeJsonFile` on `/data`. In PA7, Temporal stores the history, and the JSON files are only an audit mirror.
- Retries: PA6 had none, and `callDownstream` turned a refused connection into `downstream_unavailable`. In PA7, Temporal retries eligible failures, and `post` marks which ones to skip.
