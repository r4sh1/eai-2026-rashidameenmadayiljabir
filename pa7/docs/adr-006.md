# ADR-006 — Run the checkout saga as a Temporal workflow with retrying activities

**Status:** accepted
**Date:** 2026-10-22

## Context

My PA6 orchestrator lost the saga when it died. I slowed shipping to 2000 ms, started a checkout with key `crash-6`, and ran `docker kill pa6-orchestrator` during the shipping call.

It left a half-finished order. Payment had been called once, with amount `63.90`. Shipping had been called once. `saga-store.json` was `{"sagas": {}}`, because `persistResult` only writes at the end. `idempotency-store.json` held `crash-6` in state `in_progress`, written before the saga started.

I sent the same request again with the same key. It got `409 idempotency_conflict`: "still being processed". Nothing was processing it, and nothing would clear the record. The customer was charged and the order never finished.

Two more problems came up. A declined payment must not be retried, but a silent service should be. And shipping ran twice in the PA7 crash test.

## Decision

The workflow `checkout` in `worker/src/workflows/checkout.ts` does no I/O. It calls six activities from `worker/src/activities/index.ts`: `authorizePayment`, `reserveInventory`, `createShipment`, `sendNotification`, `refundPayment` and `releaseInventory`.

Every activity has `startToCloseTimeout` of 2500 ms, the same number as PA6's `REQUEST_TIMEOUT_MS`. It has 3 attempts, starting at 200 ms with backoff 2.

The helper `post` decides what is permanent. A `4xx` is `ApplicationFailure.nonRetryable`, because the service will say no again. A `5xx` or no answer is retryable. If the mock's error body has no `code`, `post` falls back to `<step>_failed`, as PA6 did. I set no axios timeout, so a slow call reaches the workflow as a `TimeoutFailure`.

`runStep` runs one activity and records one trace entry. `codeOf` turns the failure into a code or `timeout`. `compensate` undoes inventory, then payment. It tries every undo even if one fails. If any undo failed, the result is `failed` with `compensation_failed`. The workflow returns a `CheckoutResult` and never throws.

## Alternatives considered

I considered keeping the PA6 orchestrator and adding a recovery job at startup. The job would scan `idempotency-store.json` for `in_progress` records and finish or undo each saga.

It needs more than it looks like. PA6 knew the finished steps only in memory (`undos` in `runSaga`). I would write the saga record after every step. After a crash I still could not tell whether the call in flight had landed. In my test it had. I would also need a lock, so two orchestrators do not recover the same saga.

I rejected it: I would be building a small workflow engine myself.

## Consequences

Easier: killing the worker is no longer dangerous. In the PA7 crash test (`crash-2`), payment was called once, shipping twice, and the saga still completed.

Shipping ran twice because the first call reached the mock while the worker was dead. No engine can make that exactly once. The engine cannot know whether a call landed when the caller dies before the answer. If `authorizePayment` had run twice, the customer would be charged twice. My activities send only `orderId` and `amount`, so the payment service would have to deduplicate on `orderId`.

Slower: the crash test took about 20 s. The history showed a workflow task waiting 10 s for the dead worker.

Harder: a running workflow keeps its history. A changed `checkout` that reorders steps can fail replay, so I would need versioning.

I now run and watch a Temporal server and a worker. What breaks first: with the worker down, checkouts hang until the api gives up. I accepted that cost, plus at-least-once calls.

## What the engine took over

- Timeouts: PA6's `callDownstream` used an `AbortController` and an axios timeout, and turned `ECONNABORTED` into `timeout` by hand. In PA7 `startToCloseTimeout` does it, and `codeOf` reads a `TimeoutFailure`.
- Which steps completed: PA6 kept the `undos` array in `runSaga`, in memory, and lost it on a crash. In PA7 the workflow history holds every step's result.
- The in-progress record: PA6 wrote `in_progress` in `POST /checkout`, then `persistResult` and `releaseKey` cleared it. A crash left it forever. In PA7 the api starts the workflow with `workflowId` equal to the key and `REJECT_DUPLICATE`.
- Surviving a restart: PA6 used JSON files in `/data`. In PA7 Temporal stores the history. The files are only an audit mirror.
- Retrying: PA6 had none. A refused connection was `downstream_unavailable`. In PA7 the retry policy retries it, and `post` marks which failures to skip.
