# ADR-003 — Translate three sources into one canonical order, priced from the API

**Status:** accepted
**Date:** 2026-09-29

## Context

Three parts were hard.

**Mapping the formats.** The B2B file is windows-1257. I decoded `data/b2b-order.xml` as UTF-8 and the name came out as `Anna B�rzi�a`. No error was thrown. Decoded as windows-1257 it is `Anna Bērziņa`. Mobile sends `addr` as one comma-separated string and `ts` as epoch seconds. `fast-xml-parser` returns a lone `<LineItem>` as an object and two or more as an array. The fixture has two, so I did not run a one-item file. `translateB2B` wraps a lone object in an array anyway.

**Enriching from pricing.** `GET /pricing/PROD-013` returns `"unitPrice":4.5`. `String(4.5)` is `"4.5"`, and the schema wants two digits. `GET /pricing/PROD-999` returns `404` with `{"error":"unknown productId: PROD-999"}`.

**Removing payment data.** Web keeps it in `customer.payment`. Mobile keeps it in the top-level fields `pm`, `pan` and `pexp`. B2B keeps it in `<PaymentDetails method="wire">` inside `<BuyerParty>`, with `<IBAN>` and `<BIC>` children. The schema has no field for any of it.

## Decision

Each translator (`translateWeb`, `translateMobile`, `translateB2B`) does the same three steps. It calls `normalizeProductId`, then `enrichItems`, then builds the order field by field.

**Price format.** `toDecimalAmount` turns the API number into integer cents with `Math.round(Math.abs(price) * 100)`. It builds the string from the whole and fractional parts, and pads the fraction to two digits. PROD-013 gives `"4.50"`. I use cents only to build the string. The stored value stays a string.

**Unpriceable items.** `enrichFromPricing` returns `ok`, `unknown_product` (404) or `error` (any other failure, including a network error). `enrichItems` prices every line. A failed line is dropped and a warning is pushed. The warning has code `UNKNOWN_PRODUCT` or `PRICING_API_ERROR`, the product id, and the HTTP status if there was one. No price is invented, and never `0.00`. If every line fails, `order` is `null`, because the schema needs at least one item.

**Payment data.** I never copy the source object and delete keys. I name each allowed field and copy only those. The payment fields are never read, so they cannot leak. The three `payment-filter` tests pass.

The B2B `<UnitListPrice>` is never read. Only the API sets `unitPrice`.

## Alternatives considered

**Fail the whole order on one bad item.** This is simpler to reason about. I rejected it because one unknown product would lose a customer's whole order. The cost of my choice is that an order can leave with fewer items than the customer bought. The warning is the only trace.

**Cache prices.** This would cut API calls. I rejected it because a public test changes a catalog price and expects new output. A cache would return the old price. It would also need an expiry rule.

## Consequences

**Easier.** Any later consumer reads one shape. A catalog price change shows up in the next run.

**Harder.** Each translator builds the object separately. If the schema adds a required field, all three break at once.

**What breaks first.** A fourth source sends lowercase ids such as `prod-001`. `normalizeProductId` passes them through. `enrichFromPricing` rejects them because they do not match `PROD-<digits>`. The item is dropped as `UNKNOWN_PRODUCT` and the API is never called. Nothing crashes, but a valid product is silently lost.

**Accepted cost.** Every item makes its own HTTP call with a five-second timeout. There is no retry. One transient failure drops that item. This is fine at this scale. It would not be fine at production volume.
