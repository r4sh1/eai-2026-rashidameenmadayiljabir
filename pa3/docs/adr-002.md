# ADR-002 — Order correlation, idle timeout, and duplicate handling in the aggregator

**Status:** accepted
**Date:** 2026-09-27

## Context

The splitter turns one order into N independent item messages that travel
to different queues and get processed at different speeds, so the
aggregator has to reliably reunite them, decide when to stop waiting on a
worker, and avoid double-counting a result that gets redelivered. None of
this is optional: RabbitMQ can redeliver a message that was actually
processed but acked late, and a slow physical-item worker on a large order
is normal behaviour, not a failure. The open questions were what carries
correlation across the split, how long to wait before giving up on a
worker that never answers, what a "partial" result should actually tell
the caller, and how a duplicate result gets ignored instead of counted
twice.

## Decision

Every item message carries both `orderId` and `correlationId` (set to the
same value as the parent order's id), plus `itemIndex` and `totalItems`.
The aggregator keys its in-flight state by `orderId`, and within each
order keeps results in a dict keyed by `itemIndex` rather than a list.
Writing to an existing `itemIndex` key overwrites the previous entry,
which makes a redelivered duplicate a no-op instead of a second entry.

Timeouts are idle-based, not a fixed deadline: `last_seen` is reset in
`aggregate_result` on every message received for that order (including a
duplicate), and a background sweep thread checks every second for orders
idle past `AGGREGATOR_IDLE_TIMEOUT_SECONDS`. When an order times out, the
aggregator computes `missingItemIndexes` as the set difference between
`range(total_items)` and the received keys, and publishes
`status: "partial"` with that exact list rather than a bare "not
complete" flag.

In production I would run a longer idle timeout — 15 to 30 seconds,
longer still for heavier batch workloads — since 5 seconds only works
because the test suite's workers are fast and local; real network
latency, worker cold starts, or queue backpressure would falsely flag a
delayed-but-healthy order as partial at that setting.

## Alternatives considered

**A fixed deadline measured from order creation, instead of an idle
timeout.** Rejected because it punishes large orders: a 50-item order
needs more total processing time than a 2-item order, and a fixed timer
would call it partial even while every worker is still actively
completing items. An idle timeout only fires once activity actually
stops, so order size doesn't matter — only silence does.

**Storing aggregation state in Redis, instead of an in-memory dict.**
Rejected at this scale: it would add real deployment and operational
overhead — a service to run, a connection to manage, failure modes of its
own — for a problem an in-process dict already solves correctly. The
trade-off I accepted instead is durability, covered below.

## Consequences

This design is easier to reason about and cheaper to run: no external
store to deploy or connect to, and duplicate handling falls out of the
data structure for free instead of needing separate dedupe logic.

The real cost is durability. Because `in_flight` lives only in the
aggregator process's memory, a container crash or restart mid-order wipes
out every order currently being tracked. Any item results already
collected are lost, and any late-arriving results after the restart start
a fresh, incomplete entry for that order instead of resuming the old one
— which surfaces downstream as an order that either never completes or
completes as "partial" even though every worker actually did its job.

At ten times the traffic, this would also mean every in-flight order is
contending over the same lock around one shared dict; fine at this scale,
but it would need sharding the state or moving to an external store once
the number of concurrent in-flight orders got large enough for lock
contention itself to become the bottleneck.
