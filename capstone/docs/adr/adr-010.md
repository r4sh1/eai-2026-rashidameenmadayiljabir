# ADR-010: Stuck Saga Detection and Operator Recovery

**Date:** 2026-11-17  
**Status:** Accepted

## Context

The orchestrator stores saga progress in `saga-store.json`. Each saga contains its state, completed steps, compensation history, owner ID and `updatedAt` timestamp.

The current implementation creates a new `INSTANCE_ID` using `randomUUID()` whenever the orchestrator process starts. New sagas store this ID as their owner.

When a saga message is redelivered, the orchestrator checks whether the saga is still in the `processing` state, belongs to the current process and has `firstStepRetry` set to `true`. If the saga belongs to an earlier process, it is not resumed.

This protects against automatically repeating external operations after a restart. However, it also means that a saga interrupted while processing can remain unfinished and require manual attention.

The project requirements define a stuck-saga detection period through `SAGA_STUCK_AFTER_MS`, with a default value of 10,000 milliseconds. They also require an endpoint to list stuck sagas and another endpoint to allow an operator to compensate outstanding completed steps.

At the time of this decision, the current orchestrator source contains the ownership check and normal compensation logic, but the stuck-saga detection and operator compensation endpoints are not yet implemented.

## Decision

I chose to use a process-specific owner ID to identify sagas that were started by an earlier orchestrator instance.

A saga must not automatically resume after a restart if it belongs to a previous process. This is important because an external provider may have completed an operation even if the orchestrator did not save the result before shutting down.

The intended detection rule is to identify unfinished sagas owned by an earlier process and mark them as `needs_attention` after the configured `SAGA_STUCK_AFTER_MS` period. The detection process must publish an `order.needs_attention` outcome and record a `saga.stuck` trace event.

The intended operator recovery process is to expose `GET /sagas/stuck` and `POST /sagas/:correlationId/compensate`. Operator compensation should run only outstanding compensations for completed steps, in reverse order, using the existing provider idempotency keys.

The implementation must record the operator action in `operatorCompensation` and make repeated successful requests idempotent.

Automatic resumption was rejected. An operator should review the saga and decide when compensation is appropriate instead of allowing the system to repeat potentially completed external operations.

## Alternatives considered

1. **Automatically resume every unfinished saga after restart.**  
   This could recover some interrupted workflows, but it could also repeat payment, inventory or other external operations when the provider completed the original request but the orchestrator did not record the response.

2. **Ignore sagas owned by previous processes.**  
   The current ownership check prevents unsafe automatic execution, but leaving unfinished sagas without detection makes them difficult to identify and recover.

3. **Use a process owner ID and operator-controlled recovery.**  
   This approach prevents automatic repetition of uncertain operations while allowing an operator to inspect and recover unfinished sagas. I selected this approach.

## Consequences

The process owner ID provides a simple way to distinguish work started by the current orchestrator from work started by an earlier instance.

The main benefit is avoiding unsafe automatic retries of external operations after a restart. The trade-off is that interrupted sagas need an explicit recovery process.

The `updatedAt` field provides a timestamp that can support detection, while `SAGA_STUCK_AFTER_MS` provides a configurable waiting period.

There can be false positives. A slow provider request, temporary network delay or long-running operation may make a saga appear stuck even though the original operation is still completing. This is why the system should not automatically resume or compensate a saga merely because it is old.

Operator recovery also has risks. Compensation may fail, and an external provider may have completed an operation whose result was not recorded. Provider idempotency keys and persisted compensation history are therefore important.

**Implementation status:** Process ownership and the restriction on resuming sagas owned by earlier processes are present in the current orchestrator source. Stuck-saga detection, the required HTTP endpoints and operator compensation still need to be implemented and tested before the full ADR-010 requirements can be considered complete.
