# ADR-008: Three layers of idempotency and deduplication

**Status:** Accepted  
**Date:** 2026-11-17

## Context

The system can receive the same order more than once. A client might retry an HTTP request because it did not receive the response. RabbitMQ can also deliver a message again if a consumer fails before acknowledging it. A provider request can time out even when the provider has already completed the operation.

These situations are different, so one deduplication check is not enough. The project uses three layers: intake idempotency, saga business-key deduplication, and provider idempotency keys. The notifier also keeps its own processed-ID store.

## Decision

**1. Intake idempotency key**

The intake service requires an `Idempotency-Key` header for order submission. It stores the key, request body hash, processing state, response and correlation ID in `idempotency-store.json`.

If the client sends the same key with the same request body again, intake returns the stored response instead of creating another order. If the same key is reused with a different body, the request is rejected.

This handles a client retry where the first request was accepted but the HTTP response was lost. The saga business-key check alone would not return the original HTTP response for that same request.

**2. Saga business-key deduplication**

The orchestrator uses `source:orderId` as the business key and stores its owning correlation ID in the saga store.

If another request arrives with a different correlation ID but the same business key, the orchestrator records it as a duplicate and publishes a duplicate outcome instead of running the saga steps again.

This catches the same business order being submitted again with a new HTTP idempotency key. An intake idempotency key alone would not catch that case.

There is an important consequence: the business key remains associated with the original saga, even if that order is declined. Submitting the same `source` and `orderId` again is treated as a duplicate. A genuinely new order needs a new order ID.

**3. Provider idempotency keys**

The orchestrator sends stable keys to providers for operations that need protection against repeated execution:

- Payment authorization: `authorize:${businessKey}`
- Inventory reservation: `reserve:${businessKey}`
- Inventory release: `release:${businessKey}`
- Payment refund: `refund:${businessKey}`

The same key is reused when the operation is retried. This allows a provider that supports idempotency to avoid performing the same charge, reservation or compensation twice.

This layer protects against a provider request being completed even though the orchestrator did not receive its response. The guarantee depends on the provider actually supporting and respecting the idempotency key.

**4. Notification deduplication**

The notifier stores processed correlation IDs in `processed-ids.json`. Before sending a notification, it checks whether that correlation ID has already been processed. If it has, the message is acknowledged as a duplicate without sending another notification.

After a successful provider response, the notifier appends an entry to `notification.log`, saves the processed ID, and acknowledges the RabbitMQ message.

This reduces duplicate notifications, but it cannot guarantee exactly-once delivery. The provider could accept the notification and the notifier could crash before saving the processed ID. When RabbitMQ redelivers the message, the notifier may send it again. The notification provider request does not include an idempotency key.

## Alternatives considered

- **Use only the HTTP idempotency key:** This handles repeated requests with the same key, but not the same business order submitted with a different key.
- **Use only the correlation ID:** A new request can have a new correlation ID even when it represents the same business order.
- **Rely only on RabbitMQ message IDs:** Message redelivery and a new message representing the same business order are not the same situation. A message ID alone does not cover all these cases.
- **Make notifications exactly-once:** This would require reliable idempotency support from the notification provider. The current provider request does not send an idempotency key, so the project does not claim this guarantee.

## Consequences

The three main layers protect different parts of the order flow. They add persistent state and extra checks, but prevent many repeated operations from causing duplicate orders or charges.

Payment and inventory operations use stable provider keys so retries can be safe when the provider honours those keys. Notifications are different: the notifier's processed-ID store reduces duplicates, but delivery remains at-least-once.

There is also a business consequence of keeping the business-key mapping. A declined order cannot be submitted again using the same source and order ID as a new order. A new order ID is needed.

The system therefore favours safe retries and clear duplicate handling over claiming that every operation is exactly-once.
