# ADR-007 — Event-driven saga orchestration

**Status:** accepted  
**Date:** 2026-11-17

## Context

The intake service receives an order through HTTP, but the order processing takes several steps and can involve external services. I did not want the HTTP request to stay open while the whole saga runs.

The orchestrator therefore receives orders from RabbitMQ through `saga.queue`. This separates accepting an order from processing it. Intake can return `202 Accepted` after the order has been published successfully, while the orchestrator works on it in the background.

There are also a few reliability points to consider:

- A message should not be acknowledged before its processing result has been saved.
- If the orchestrator saves a final state but crashes before publishing the outcome, the saved outcome should still be available for publishing again.
- The number of messages being processed at the same time should be controlled.
- Intake needs to keep the order status updated without allowing old events to move it backwards.

## Decision

I used RabbitMQ events to start the saga instead of making a direct HTTP call from Intake to the orchestrator.

The orchestrator consumes messages from `saga.queue`. It uses `SAGA_CONCURRENCY` to set RabbitMQ prefetch, with a default value of 5 and a minimum of 1. This limits the number of unacknowledged messages delivered to the consumer. It does not mean that every message is processed by a separate worker.

The orchestrator saves saga progress to its persistent saga store. When a final outcome is created, it first saves the final state and the outcome envelope. After that, it publishes the event to the `orders.outcome` exchange and waits for RabbitMQ publisher confirms.

The original saga message is acknowledged after successful processing. When processing needs a retry, the orchestrator uses `nack` so RabbitMQ can move the message through the configured retry route. If an unexpected error occurs, the message is not acknowledged.

For order status, Intake stores the accepted order before publishing it. It then consumes lifecycle events from `intake.outcome.queue` and updates the stored order record. The `GET /orders/:correlationId` endpoint uses this stored record to return the current status.

I also added transition rules in Intake. For example, an order in a terminal state such as `completed`, `failed`, `compensated`, or `duplicate` cannot move to another state because of a later event. Invalid transitions are ignored.

## Alternatives considered

**Keeping the whole workflow inside the HTTP request**

This would make the request wait for payment, inventory, shipping, and notification steps. It would also make the intake service more dependent on the availability and response time of every service. I chose asynchronous messaging instead.

**Calling the orchestrator directly over HTTP**

This would connect Intake and the orchestrator more tightly. RabbitMQ gives the orchestrator a durable queue to receive work and makes retries easier to manage.

**Acknowledging a message immediately after receiving it**

This could lose work if the service crashes before saving the result. I chose to acknowledge only after successful processing and saving the required state.

**Publishing the final event before saving the final state**

If the service crashed after publishing but before saving, the stored saga state could disagree with the event already sent. I chose to save first and publish second.

**Using unlimited message delivery**

This could allow too many messages to be delivered to the orchestrator at once. I used prefetch controlled by `SAGA_CONCURRENCY` to limit unacknowledged deliveries.

## Consequences

The HTTP request does not need to wait for the full order workflow. RabbitMQ separates order acceptance from saga processing, and the orchestrator can control how many messages it handles at a time.

Saving the outcome before publishing also gives the orchestrator a way to publish the stored outcome again if the original message is delivered again after a failure. This is important because the save and publish operations are not one atomic transaction. There can still be a short period where the final state is saved but the outcome has not reached Intake yet.

The system must therefore tolerate repeated outcome events. Intake's transition checks help prevent an old event from moving an order backwards, and the orchestrator can replay a saved outcome when it receives a message for a saga that already has a final outcome.

The trade-off is that the implementation is more complex than a simple synchronous request. It needs persistent saga state, message acknowledgements, retry handling, outcome events, and status transition rules.
