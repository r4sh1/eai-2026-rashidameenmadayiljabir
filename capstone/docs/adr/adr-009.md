# ADR-009: Wire-tap tracing and causation tracking

**Status:** Accepted  
**Date:** 2026-11-17

## Context

The project has several services involved in one order: intake, orchestrator, notifier and observer. When an order fails or is retried, I need to understand which service handled it, what happened, and which previous operation caused the next one.

I considered three approaches: a wire tap using RabbitMQ, scatter-gather tracing, and OpenTelemetry. Scatter-gather would make the services wait for trace responses, which is not suitable for this workflow. OpenTelemetry is a useful standard, but it would introduce another tracing setup and dependency for this capstone. I chose a simple RabbitMQ wire tap because the project already uses RabbitMQ for communication.

## Decision

Every service creates trace hops using the shared `beginTraceHop()` helper in `shared/trace.ts`. Each hop receives a UUID, correlation ID, causation ID, service name, operation name, attempt number, status and timestamps.

When the operation finishes, the helper publishes the hop to the `trace.events` fanout exchange. The observer receives these messages through `trace.store` and appends them to `/data/trace-store.jsonl`. The trace can then be read through `GET /trace/:correlationId`.

**Trace publishing is fire-and-forget.** The helper calls `channel.publish()` but does not wait for publisher confirms. It catches synchronous publishing errors and logs them. This is intentional: tracing must not block or fail the actual business operation.

The trade-off is that a hop can be lost if publishing fails or the broker is unavailable. The order may still complete, but its trace can be incomplete. This is acceptable for the current design because tracing is used for debugging and observability, not as the source of truth for order state.

For causation, each published message carries the `hopId` of the hop that published it in its `causationId` header. The next consumer uses that value for its first trace hop.

There is a special case with retries. RabbitMQ `nack` cannot rewrite message headers, so every delivery attempt of the same message keeps the original publisher's causation ID. The attempt number changes using the retry information from `x-death`. Each failed attempt also creates a retry hop caused by that attempt's consume hop.

For an explicit DLQ replay, the replay operation creates a new hop. The replayed message then carries the replay hop's ID as its causation ID.

The observer is separate from the business services. If it is unavailable, trace records may not be collected while it is down. The business workflow should continue because the trace helper does not wait for the observer or publisher confirmation.

## Alternatives considered

- **Scatter-gather:** Each service could request tracing information and wait for a response. I rejected this because it would add communication overhead and make business processing depend on another service.
- **OpenTelemetry:** This would provide a standard tracing solution with broader integration options. I did not choose it because the current capstone requirements can be handled with the existing RabbitMQ infrastructure and a small shared helper.
- **Publisher-confirmed trace events:** Waiting for broker confirmation would provide stronger evidence that a hop was accepted by RabbitMQ. I rejected this because a tracing problem could delay or interfere with the business operation.
- **Writing traces directly to a local file in every service:** This would make trace collection harder across multiple containers and would duplicate storage logic.

## Consequences

The wire tap keeps tracing separate from the main order workflow. Services can publish trace events without waiting for the observer, and the observer stores them centrally for later inspection.

The main disadvantage is that tracing is best-effort. A lost event can leave a gap in the trace, and a temporary observer outage can make debugging less complete. The trace must therefore not be treated as proof that a business operation succeeded or failed.

The causation rules also need to be followed carefully, especially during retries and DLQ replay. Keeping the original causation ID across RabbitMQ redeliveries, while recording a separate attempt number and retry hop, makes it possible to understand the full retry history.
