# ADR-011 — Temporal workflow orchestration

**Status:** accepted  
**Date:** 2026-11-19

## Context

The hand-rolled orchestrator already coordinates the order saga, but it also has to implement process ownership, message redelivery handling, retry scheduling, and recovery after a process restart. PA7 introduced Temporal as a durable workflow engine. The capstone keeps the hand-rolled path as the default and adds Temporal as an optional engine so both implementations can process the same accepted-order event.

The important boundary is that Temporal owns durable workflow execution, while the application still owns order rules and external side effects.

## Decision

When `SAGA_ENGINE=temporal`, the orchestrator consumes `order.accepted` from `saga.queue` and starts the workflow type `checkout` with `workflowId` equal to the `businessKey`, on the `checkout` task queue in the `default` namespace. It records a `workflow.start` trace hop after attempting the start. If Temporal reports that the workflow already exists for the same business key and correlation ID, the message is treated as a redelivery and acknowledged. If the business key is already associated with another correlation ID, the orchestrator emits a `duplicate` outcome instead of starting another workflow.

The workflow in `worker/src/workflows/checkout.ts` contains the checkout sequence and B2B branch. Provider requests, trace hops and lifecycle/outcome publishing are activities in `worker/src/activities/index.ts`; workflow code does not publish directly to RabbitMQ. The activity retry policy is three attempts, a 200 ms initial interval, a backoff coefficient of 2, and a 2,500 ms start-to-close timeout. HTTP 4xx provider responses are marked non-retryable.

## Alternatives considered

- **Keep only the hand-rolled saga.** This avoids operating Temporal, but leaves retry scheduling and durable workflow recovery in application code.
- **Move the entire application into Temporal.** This would unnecessarily move intake, normalization, RabbitMQ topology, trace storage and notification delivery into the workflow engine.
- **Start a new workflow for every delivery.** This would allow duplicate workflows and repeated business effects, so the stable business key is used as the workflow ID and duplicate starts are acknowledged.

## Consequences

Temporal provides durable workflow history and replays workflow code after worker restarts. Activity retries are centrally scheduled according to the configured policy, and the workflow sequence is visible in the Temporal UI.

The system now has another service to operate and monitor. External provider effects still need idempotency because an activity can be retried after a timeout or worker failure. In the observed worker-crash test, payment and inventory effects remained single effects, but the shipping mock recorded a repeated create attempt while the request was in flight. The Temporal activity also publishes outcome events without waiting for RabbitMQ publisher confirms, so outcome delivery is not confirmed before the activity completes.

## What the engine took over

- **Durable workflow state and replay.** The hand-rolled path stores saga progress in `orchestrator/src/index.ts` through `runSaga()` and the saga store. Temporal stores workflow history and replays `checkout()` from `worker/src/workflows/checkout.ts`.
- **Workflow task scheduling and dispatch.** The hand-rolled path runs the ordered steps inside `runSaga()` in the orchestrator process. Temporal schedules workflow tasks on the `checkout` task queue and dispatches them to the worker.
- **Activity retry and timeout scheduling.** The hand-rolled path applies provider retry handling in the orchestrator's provider-call path. Temporal applies the activity retry policy declared by `proxyActivities()` in `worker/src/workflows/checkout.ts`.
- **Recovery of workflow execution after a worker restart.** The hand-rolled path marks work owned by a previous process as `needs_attention` in `markPreviousProcessSagasAsStuck()`. Temporal retains workflow history and can resume workflow execution when a worker polls again.

Temporal did **not** take over:

- Intake, payload normalization, validation, pricing enrichment or HTTP idempotency.
- RabbitMQ topology and consumption of `saga.queue`, or the decision to start a workflow.
- Business-key deduplication in the orchestrator.
- Provider HTTP APIs, provider-side idempotency keys, or the business meaning of payment, inventory and shipping operations.
- Trace-hop creation, outcome-event construction and publication, the notifier, or the observer.
- Human operational policy. The hand-rolled operator compensation endpoint does not control Temporal workflows; Temporal workflow compensation is performed by the workflow itself.
