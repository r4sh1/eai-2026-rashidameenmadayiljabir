# ADR-001 — Reliable Asynchronous Messaging with RabbitMQ, Publisher Confirms, Durable Queues, and Manual Acknowledgements

**Status:** accepted  
**Date:** 2026-09-22  

## Context

In our architecture, order ingestion (`POST /publish`) must remain decoupled from backend processing (the consumer appending to `data/received.jsonl`). Because the downstream consumer may be slow, offline for maintenance, or experiencing transient failures, synchronous HTTP processing is unsuitable. To ensure zero message loss across broker failures and process crashes, we must address four fundamental messaging decisions:

1. **Queue Durability**: A non-durable queue definition exists only in broker memory. If `pa2-rabbitmq` is restarted (e.g. via `docker restart pa2-rabbitmq`), a non-durable queue and all queued messages are lost immediately upon shutdown.
2. **Publisher Confirmation & Message Persistence**: When `POST /publish` returns `202 Accepted`, it promises the HTTP caller that the message is durably stored in the broker. Under `X-Publish-Mode: fire-and-forget`, messages are published without `persistent: true` and without waiting for a broker confirm callback. In demonstration (c) (`04-publisher-confirms-prevents-loss.test.ts`), killing the RabbitMQ broker (`docker kill pa2-rabbitmq`) results in deterministic message loss for unconfirmed, non-persistent messages sitting in the queue.
3. **Consumer Acknowledgement Strategy**: Under automatic acknowledgement (`noAck: true`), RabbitMQ removes a message from the queue the moment it is dispatched. If the consumer crashes during execution or disk write, the message is permanently lost. Furthermore, acking *before* appending to disk creates a race condition where a crash between `ack()` and `appendFileSync()` loses the message.
4. **End-to-End Correlation ID Propagation**: Distributed trace visibility requires tracing an order from the initial HTTP request to the final log record in `data/received.jsonl`. Storing correlation IDs inside payload bodies is fragile and violates protocol boundaries; propagation must occur via standard AMQP protocol message properties (`properties.correlationId`).

## Decision

We implemented a durable, confirmed publishing and manually acknowledged consuming pipeline across `producer.ts` and `consumer.ts`:

1. **Durable Queue Assertion**: Both `connectProducerChannel` and `connectConsumerChannel` assert the queue with `{ durable: true }` via `channel.assertQueue(queueName, { durable: true })`. This guarantees the queue metadata and persistent queue contents survive broker restarts.
2. **Publisher Confirms & Persistent Delivery**: In `connectProducerChannel`, we establish a `ConfirmChannel` via `connection.createConfirmChannel()`. In `publishMessage`:
   - For standard `confirmed` mode, messages are published with delivery mode `{ persistent: true, correlationId }`, and the function returns a Promise that resolves only when RabbitMQ invokes the confirmation callback. HTTP `202 Accepted` is sent strictly after confirmation.
   - For `fire-and-forget` mode (used strictly for risk demonstration), messages are published with `{ persistent: false }` without awaiting confirmation.
3. **Post-Write Manual Acknowledgement**: In `connectConsumerChannel`, we set a prefetch limit (`channel.prefetch(10)`) and consume with `{ noAck: false }`. In `handleMessage`, the consumer first writes the JSON record (`correlationId`, `receivedAt`, `payload`) to disk using `appendFileSync(OUTPUT_PATH, ...)` and invokes `channel.ack(msg)` **only after** the disk write completes successfully.
4. **Correlation ID Validation & AMQP Header Mapping**: `handlePublish` validates supplied `X-Correlation-Id` headers against `/^[A-Za-z0-9._-]{1,128}$/` (or generates a UUID v4 if missing). The validated ID is mapped to `options.correlationId` in `publishMessage`, transmitted as AMQP `msg.properties.correlationId`, and extracted verbatim in `handleMessage` for output into `received.jsonl`.

## Alternatives considered

1. **Auto-Ack (`noAck: true`) or Acking Before Disk Write**: We considered acking messages immediately upon receipt to maximize throughput. However, if `appendFileSync()` fails (e.g., disk full, permission error) or the process terminates unexpectedly mid-write, the message is unrecoverably lost because RabbitMQ already purged it.
2. **Unconfirmed Publishing (`channel.publish()` returning boolean)**: Naive implementations rely on `channel.publish()` return values for backpressure, returning `202` immediately. However, `channel.publish()` returning `true` only indicates network buffer capacity in the node process—it provides zero guarantee that RabbitMQ has received or flushed the message to disk. We rejected this in favor of `ConfirmChannel` callbacks.
3. **Embedding Correlation ID in Payload Body**: We considered injecting `correlationId` into the JSON payload body. This was rejected because payload schemas belong to domain logic, whereas correlation tracing is an infrastructure concern. Utilizing AMQP's native `properties.correlationId` preserves clean separation of concerns.
4. **Default Guest Credentials**: Retaining `guest`/`guest` was rejected in favor of dedicated non-loopback credentials (`eai:eai-pa2`) as guest logins are restricted to loopback interfaces by default in RabbitMQ.

## Consequences

- **Guarantees Achieved**: The system guarantees zero message loss across broker restarts (`02-broker-restart-survives.test.ts`), retains pending messages during consumer downtime (`03-consumer-stopped-accumulates.test.ts`), and provides strong guarantees to HTTP callers that `202 Accepted` represents durable broker storage.
- **Latency & Throughput Trade-offs**: Awaiting publisher confirmation per HTTP request introduces network round-trip latency (typically 5–20ms per publish). Synchronous disk writes (`appendFileSync`) on the consumer limit single-thread throughput.
- **Backpressure & Queue Growth**: If the consumer is offline for an extended period, messages accumulate in the durable queue. While RabbitMQ stores persistent messages on disk, extreme queue depth (e.g. millions of messages) will consume broker disk space. If disk space exceeds high-water marks, RabbitMQ blocks publishers.
- **At-Least-Once Delivery & Idempotency**: If the consumer appends a line to `received.jsonl` but crashes before `channel.ack(msg)` executes, RabbitMQ will redeliver the message upon consumer reconnect. The consumer accepts at-least-once delivery semantics; downstream deduplication based on `correlationId` is required if strict exactly-once processing is needed.
